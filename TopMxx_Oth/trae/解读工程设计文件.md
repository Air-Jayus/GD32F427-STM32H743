**开发商**：杭州科强智能控制系统有限公司  
**目标芯片**：GD32F427VGT6 (Cortex-M4, 200MHz)  
**软件版本**：V2.65 (主机软件系列 8100)  
**项目理念**：新一代注塑机控制器的软、硬件平台，追求**易扩展、易维护**

这是一个完整的**液压/伺服注塑机嵌入式控制系统**，涵盖了注塑机从合模、注射、保压、储料到开模、顶针等全部核心动作的控制逻辑。

## 🧠 Application 目录 - 业务核心层

### 1. Scheduler（调度器）- **系统的大脑**

这是整个系统最精巧的部分。注塑机经常出现**并行动作**（如开模同时吹气、冷却同时润滑），调度器通过**7条流程（Flow）** 实现：

| 流程号 | 用途 |
|--------|------|
| Flow[0] | **主流程** - 关模→注射→保压→储料→开模→顶针 全循环 |
| Flow[1] | **吹气** - 可与主流程并行 |
| Flow[2] | **自动门** - 安全门控制 |
| Flow[3] | **气辅** - 气辅注射 |
| Flow[4] | **连动** - 中子连动、顶针连动 |
| Flow[5-6] | **润滑1/2** - 可与主流程并行的周期性润滑 |

**调度请求机制**（8种优先级）：
```
eFRQ_NewFA      新建动作（按下按键）
eFRQ_InsConAct  插入继续
eFRQ_InsReAct   插入重新开始
eFRQ_FinAct     正常结束
eFRQ_BrkAct     异常中断（警报/超时）
eFRQ_KeyBrkAct  按键中断
```

每个动作状态机有 **RunState**（Init→Start→Run→HangRdy→Hang→End）和 **ActStep**（TStartN→TStartS→...→TEndN 共255个步骤），实现了：
- 动作可被插入、挂起、恢复
- 子动作可在 TStart/TEnd 多个时刻插入
- 中子、机械手在动作开始/中途/结束不同时机执行

### 2. Action（动作框架）- **动作的骨架**

定义了动作的**段结构**：
```
ActionStr（动作）
  └─ SectionStr[]（段数组，最多28段）
       ├─ SecDOStr（DO输出表）：延时、时间、动作结束关延时
       ├─ SecDAStr（DA输出表）：斜率、延时、值、比例
       ├─ SecEndCondStr（结束条件）：位置到/时间到/DI为真
       └─ SecCallFunP（段函数）：段跳转、非标逻辑
```

### 3. Alarm（警报系统）
支持警报设置（带属性：闪烁/保存/蜂鸣/动作限制）、清除、背景警报、指令限制。

### 4. Monitor（生产监测）
监测18个对象：循环时间、关模时间、开模结束位置、注射时间/速度/峰值压力、储料时间/转速等，支持上限/上下限检查，超差可触发警报或提示。

### 5. Position（位置处理）
5路电子尺（模板/螺杆/顶针/座台/模厚）+ 3路模拟量，提供位置比较、范围检查、速度计算。

### 6. Temp（温度处理）
多段料筒温度闭环（开料筒加热器）、油温/电机温度监测、防冷启动保护。

### 7. Wave（示波器）
支持**10种触发模式**（连续/循环/开模/关模/注射/储料/射退/顶针），3种采样间隔（10ms/20ms/50ms），2048点环形缓冲，支持波形触发轴切换。

### 8. Code（指令解析）
定义了完整的**按键指令集**（55个动作指令 + 5种模式切换 + 18种调试指令），支持IO强制输出、DA强制输出、电子尺归零/校长度、参数重置、开模参数自学习等。

### 9. HAI / DateTime / Boot_IAP / License / Fun / AuxDef / SysDef / Include
- HAI：液压模拟量（注射压力/锁模压力驱动器实时值读取、锁模力纠偏）
- DateTime：RTC日期时间
- Boot_IAP：APP下载更新（串口Bootloader）
- License：功能授权管理
- SysDef：系统常量（200MHz主频、软件版本号、中断优先级）

## ⚙️ Action 目录 - 动作编排层

### AL_ 前缀：动作逻辑（Action Logic）
负责**条件判断、异常处理、中断属性配置**，不直接输出DO/DA，而是调用AU执行。典型的：

| 文件 | 功能 |
|------|------|
| AL_MoldCls | **关模逻辑** - 检查安全门、机械保险、液压保险、先导油压，失败则触发开模 |
| AL_MoldOpen | **开模逻辑** - 检查顶针位置、中子状态，自动循环时开模后处理 |
| AL_Inject | **注射逻辑** - 检查螺杆位置、安全门、喷嘴、油温电机温度 |
| AL_Charge | **储料逻辑** - 检查温度、转速，处理储料超时 |
| AL_SuckBack | **射退逻辑** - 储前射退/储后射退/冷后射退三种时机 |
| AL_EjeFor/AL_EjeRet | **托进/托退逻辑** |
| AL_NozFor/AL_NozRet | **座进/座退逻辑** |
| AL_MotorOn/AL_MotorOff | **马达开关逻辑** - 检查油温/电机温度、驱动器状态 |
| AL_AssAct | **自动循环辅助** - 循环开始/结束/计数/电眼检物 |
| AL_Lubr | **润滑逻辑** - 按键润滑/自动润滑/开机润滑 |
| AL_Robot | **机械手逻辑** - 等待机械手信号/循环启动握手 |
| AL_SafeGate | **安全门逻辑** - 开关安全门的联锁条件 |

### AU_ 前缀：动作单元（Action Unit）
负责**具体的DO/DA输出执行**，按段（Section）顺序执行。典型的：

| 文件 | 段ID | 功能 |
|------|------|------|
| AU_MoldCls | Start→MC1→MC2→MC3→LP→HP→HPDly | 关模7段（一段→二段→三段→低压→高压→高压保持） |
| AU_Inject | Inj1~Inj10 + HP1~HP10 | 注射10段 + 保压10段 |
| AU_MoldOpen | SpeUp→MO1~MO3→Break→End | 开模加速段/多段/刹车 |
| AU_EjeFor | EF1~EF5 | 托进5段 |
| AU_Nozzle | SPNozzle/DPNozzle | 单向/双向喷嘴开关 |

### ActConf（动作配置）
整个动作系统的**总配置中心**：
- 定义所有动作的 **ActGroup**（动作组）、**ActFunID**（函数ID，全局唯一）、**ActSeg**（细分）
- 配置 **33路RI数字滤波**（紧急停止、安全门、伺服异常、油位等）
- 提供**标准动作配置**（ActConf_Std），适用于常规全液压式注塑机（海天SA系列、天剑PL系列）
- 包含**RPHA参数读写**功能：机器参数/生产参数/硬件配置/警报的铁电存储

## 🎯 总结：这个项目实现了什么

**一句话**：一个功能完整的**注塑机嵌入式控制系统**，覆盖了从硬件驱动、位置/温度采集、伺服通讯、调度编排、到注塑工艺控制的全栈。

**核心特色**：
1. **动作框架设计精巧** — AL(逻辑层) + AU(执行层) 双层架构，通过统一的段结构（DO/DA输出表+结束条件）和调度器（7条并行流程+8级优先级），实现了动作可插拔、可中断、可并行执行
2. **多品牌伺服兼容** — 同时支持台达、艾普、蒙德、伟创、海天等主流伺服，通过CANopen协议（PDO/SDO）通讯
3. **生产监测系统** — 18项工艺参数实时监测（循环时间/位置/压力/速度），超差自动警报
4. **完整的注塑工艺覆盖** — 自动调模、锁模力纠偏、排气、气辅注射、BMC加料、机械手联协、电眼自动循环等高级功能
5. **参数持久化** — FRAM铁电存储 + RPHA参数管理，支持掉电保存
6. **可扩展性** — 通过ActConf可配置不同机型（二板机/三板机/双色机等），伺服驱动可按需启用

关于你问的 **Action 和 Application 文件夹是否重要**：

**Application 是核心大脑** — 调度器Scheduler决定动作什么时候执行、并行流程如何同步；Action决定动作具体怎么输出；两者加起来就是整个注塑机的**动作控制引擎**。没有它们，这个项目就只是一堆底层驱动的集合。

### 问题二：读计数器值怎么就变成"系统时间"了？

关键在 [Time_Drv.c](file:///D:/TopMxx_Oth1/TopMxx_Oth/Driver/Time_Drv.c#L77-L94) 的初始化配置和第 29-31 行的注释：

```c
// 初始化配置（Time_Drv.c 第91-94行）
timer_initpara.prescaler   = 2000-1;       // 200MHz / 2000 = 100kHz → 每10us计1次
timer_initpara.period      = 0xffffffff;   // 32位计数器，自由运行，永不复位
timer_initpara.counterdirection = TIMER_COUNTER_UP;  // 一直往上数

timer_enable(TIMER1);  // 启动后，这个计数器就一直在跑，永不停
```

**设计思路**（Time_Drv.c 第29-31行注释说得清楚）：

> 3、定时器的定时单位10us，最大12.7h，各时间计算均以其为参考。  
> 4、由于主循环周期不固定，为保证动作中延迟等的时间精度，不采用给出定时中断标志并以其为计时基础的方式，而采用**保存系统时间（CNT），然后通过计算某时刻与系统时间差值的方式**，来得到准确的经过时间。

通俗讲就是：

```
这个定时器就像一块"秒表"，启动后一直往上数：
  0 → 1 → 2 → 3 → ... → 0xFFFFFFFF → 0 → 1 → ...（约12.7小时溢出一次）

"系统时间" = 秒表当前读数 = TIMER_CNT(TIMER1)

你要计时的时候：
  1. 复位计时器：记下此刻秒表读数 → StartTime = GetSysTime()
  2. 过一会儿：读此刻秒表读数 → 当前 = GetSysTime()
  3. 经过时间 = 当前 - StartTime  （做减法）
```

例如 [G10usTimerCal](file:///D:/TopMxx_Oth1/TopMxx_Oth/Driver/Time_Drv.c#L333-L336) 就是这么实现的：

```c
U32 G10usTimerCal(G10usTimer *Timer)
{
    return (GetSysTime() - Timer->StartTime);  // 当前读数 - 开始读数 = 经过时间
}
```

这种设计的好处是：**不依赖中断**。传统做法是用定时中断每10us产生一个tick，然后数tick。但如果主循环卡了，tick会丢。这里用**自由运行计数器做差值**，无论主循环多慢，时间都准。

差值法不存在这个问题：计数器是纯硬件在跑，不受 CPU 执行状态影响。无论主循环卡多久、中断嵌套多深，CNT 都在精确递增。你什么时候来读，读到的都是**真实物理时间**。

```c
// 本工程：主动做减法
if (G10usTimerOver(&t, T1msTo10us(5))) { /* 超时5ms */ }
```

这意味着动作状态机可以在**每个循环周期**都检查超时，而不是只能在中断里才知道。

**4. 分辨率灵活**

两个计数器覆盖了两个量级：

| 计数器 | 分辨率 | 溢出周期 | 用途 |
|--------|--------|---------|------|
| TIMER1 (TIM2) | 10us | ~12.7小时 | 常规计时（动作延迟、循环时间） |
| TIMER4 (TIM5) | 10ns | ~429秒 | 高精度计时（Dly1us、EtherCAT） |

### 关键在 C 语言无符号整数减法的回绕特性

U32 减法是 **mod 2³² 运算**，也就是自动取模。举个具体数字：

```
假设 StartTime = 0xFFFFFFF0  （溢出前16个tick）
当前CNT     = 0x00000010  （溢出后16个tick）

实际经过   = 16 + 16 = 32 个tick

U32减法：  0x00000010 - 0xFFFFFFF0
         = 0x00000010 - 0xFFFFFFF0
         = 0x00000010 + (0x100000000 - 0xFFFFFFF0)   ← 借位
         = 0x00000010 + 0x00000010
         = 0x00000020
         = 32  ✓
```

CPU 做无符号减法时，不够减就自动"借位"——这个借位正好就是溢出掉的那个 2³²。所以**一次溢出范围内的减法，结果天然正确**。

### 硬件层面理解

32 位计数器溢出回绕，本身就是 **mod 2³² 计数器**。CNT 的值本质上是：

```
CNT = 真实总tick数 mod 2³²
```

那么：

```
当前CNT - 起始CNT = (真实总tick数 mod 2³²) - (起始总tick数 mod 2³²)
                   = (真实经过tick数) mod 2³²
                   = 真实经过tick数    ← 只要经过量 < 2³²
```

数学上严格成立。只要计时间隔不超过 2³² 个 tick，无论中间溢出多少次（其实最多溢出一次），减法结果都精确。

### 这个"自动重装影子"是干什么的

它设置 CTL0 的 ARSE 位，控制**周期寄存器（CAR）的写入何时生效**：

```
ARSE=0（影子关闭）：你写CAR的瞬间，新值立即生效
ARSE=1（影子开启）：你写CAR，新值先存在影子寄存器，等下一个更新事件（溢出）才生效
```

影子机制存在的意义是：**定时器运行中动态改周期时，避免中途毛刺**。比如计数器当前走到 5000，你突然把周期从 6000 改成 3000，如果立即生效，计数器得一直走到 0xFFFFFFFF 才回绕，时序会乱；影子开启后，它会等这一轮计数干净结束、在更新点才切换。

### 为什么本工程里开不开都一样

因为这两个定时器：

1. **周期在初始化时只写一次**：`period = 0xffffffff`，之后运行期间**从不修改**
2. **`timer_init` 内部已经主动触发过一次更新事件**（[gd32f4xx_timer.c#L183](file:///D:/TopMxx_Oth1/TopMxx_Oth/GD32F4xx_Firmware_Library/GD32F4xx_standard_peripheral/Source/gd32f4xx_timer.c#L183) 的 `TIMER_SWEVG_UPG`），即使影子开着，初始化值也已经立即装载了
3. **都不做 PWM 输出**（那段 PWM 代码全部注释掉了），纯粹是自由计数器做差值

所以 ARSE 位对这两个定时器的实际运行**没有任何影响**。它只在"运行中改周期"时才起作用，而本设计根本没有这个场景。

### 假设打开，它想干什么——"滚动比较值"产生周期中断

看函数体核心 [Time_Drv.c#L233-L238](file:///D:/TopMxx_Oth1/TopMxx_Oth/Driver/Time_Drv.c#L233-L238)：

```c
if(SET == timer_interrupt_flag_get(TIMER1, TIMER_INT_FLAG_CH0)) 
{
    TIMER_CH0CV(TIMER1) = TIMER_CH0CV(TIMER1) + 100000;  // 比较值往前推
    timer_interrupt_flag_clear(TIMER1, TIMER_INT_FLAG_CH0);
}
```

`CH0CV` 是通道 0 的比较寄存器。自由计数器 CNT 一直往上数，当 **CNT 追上 CH0CV** 时产生匹配中断。中断里不复位 CNT，而是把 CH0CV 再往前加 `100000`，于是下一个匹配点在 100000 个计数之后。

```
100kHz（10us/tick）下：100000 × 10us = 1,000,000us = 1 秒
```

所以它的设计意图是：**每隔 1 秒产生一次周期中断**。

### 为什么要这么绕，不直接用溢出中断？

这是这套计时方案的精髓所在。普通定时器做周期中断，是靠"数到周期值→复位归零→重来"，但那样 CNT 会被反复清零，就**没法当绝对时间基准做差值计时了**。

而"滚动比较值"两者兼得：

```

CH0CV：    100000 → 200000 → 300000 → ...（每1秒被CNT追上一次，产生周期tick）
```

### 先理解普通周期中断（需要清零）

普通定时器做周期中断，靠的是"数到顶就归零"：

```
计数方向 ↑
CNT:  0 ──→ 999 ──→ 0 ──→ 999 ──→ 0 ──→ 999
              │溢出中断      │溢出中断      │溢出中断
              ↓             ↓             ↓
             10ms          20ms          30ms

问题：CNT 每次都被清零 → 无法当"绝对时间"做差值计时
```

### 再理解比较匹配中断

定时器除了"数到顶溢出"，还有一种中断叫**比较匹配**：硬件持续比较两个值——计数器 CNT 和比较寄存器 CH0CV，**一旦 CNT == CH0CV 就触发中断**。CNT 继续往上数，不受影响。

```
CNT:    0 ──→ ... ──→ ★100000 ──→ ... ──→ 继续往上数，永不停
                       │
                  CNT==CH0CV，触发中断
                       ↓
                     1秒到了
                  （但CNT不归零，继续跑）
```

关键就在这：**匹配只"报警"，不动 CNT**。

### 滚动比较值：把"一次性报警"变成"周期报警"

匹配中断只在 CNT 追上 CH0CV 的那一瞬间触发一次，之后 CNT 就跑过去了。要让它**每隔 1 秒触发一次**，就在中断里把 CH0CV 往前推一格：

[Time_Drv.c#L235](file:///D:/TopMxx_Oth1/TopMxx_Oth/Driver/Time_Drv.c#L235)：
```c
TIMER_CH0CV(TIMER1) = TIMER_CH0CV(TIMER1) + 100000;  // 比较值 +100000
```

时间轴变成这样（每格 100000 计数 = 1 秒）：

```
CNT(自由跑): 0 ──────────────→ 100000 ──────────────→ 200000 ──────────────→ 300000 ──→
                                ★匹配                 ★匹配                 ★匹配
CH0CV(往前滚):              =100000              =200000              =300000
                                │                    │                    │
                              中断①                中断②                中断③
                           CH0CV+=100000        CH0CV+=100000        CH0CV+=100000
                           (改成200000)         (改成300000)         (改成400000)
                                ↓                    ↓                    ↓
                              1秒                  2秒                  3秒
```

CNT 从头到尾**一次都没清零**，平滑地往上跑；只是 CH0CV 这个"报警点"每次被推到下一个 100000。于是：

- **差值计时照常用**：`GetSysTime()` 读的就是这条一直增长的 CNT
- **周期中断也有了**：每滚一格报警一次，间隔恒为 100000 tick = 1 秒

### 为什么间隔精确、不会累积误差

因为每个报警点是**绝对位置**（100000、200000、300000...），不是"从中断时刻起再等 100000"。即使某次中断因为高优先级任务延迟了几十微秒才进 ISR，CH0CV 改成的是"下一个绝对点"，CNT 到那个绝对点照样触发，**误差不累积**。

这也是为什么用 `CH0CV = CH0CV + 100000`（基于当前比较值推），而不是 `CH0CV = CNT + 100000`（基于当前计数推）——后者会把中断响应延迟带进周期里。

### 一个必须注意的细节

CH0CV 也是 32 位，会跟着溢出回绕。但因为 CNT 和 CH0CV 用同样的无符号回绕规则做硬件比较，跨过 `0xFFFFFFFF → 0` 时比较依然成立，周期不乱。这和我们前面讲的 U32 减法天然处理溢出是同一个道理。

### 一句话总结

> 普通周期中断靠"清零重来"，破坏了绝对时间；滚动比较值靠"报警点往前挪一格"，CNT 永不复位——既保住了自由计数器当时间基准，又得到了周期性中断。这是"差值计时"和"周期 tick"两个需求冲突时，用比较匹配功能做的一个调和。

### 1. 它们存的值，时间基准不一样

| 类型 | 配套函数 | Cal返回值单位 | Over的比较值单位 |
|------|---------|-------------|----------------|
| G10nsTimer | G10nsTimerCal/Over | 10ns | 10ns |
| G10usTimer | G10usTimerCal/Over | 10us | 10us |
| G10msTimer | G10msTimerCal/Over | 10ms（内部/1000） | 10ms |
| G100msTimer | G100msTimerCal/Over | 100ms（内部/10000） | 100ms |

你声明 `G10msTimer t;` 时，类型名就在提醒你：`G10msTimerOver(&t, 5)` 里的 5 是"5 个 10ms = 50ms"，不用自己换算 tick。单位换算被封进了函数里，使用者只用业务单位。

### 3. 为什么不用 typedef 起别名

你说的写法是这样：

```c
typedef struct { U32 StartTime; } GTimerBase;
typedef GTimerBase G10nsTimer;
typedef GTimerBase G10usTimer;   // 别名 → 编译器眼里它们是"同一个类型"
```

这样 `G10nsTimer*` 和 `G10usTimer*` 是**完全相同的类型**，编译器、静态检查器都分不清，你把 10ns 的计时器传给 10us 的函数，连个警告都不会有。

而现在这种"**各自独立的匿名 struct**"写法：

```c
typedef struct { U32 StartTime; } G10nsTimer;
typedef struct { U32 StartTime; } G10usTimer;  // 这是另一个不同的 struct 类型
```

在 C 里每写一次 `struct { ... }` 就产生一个**新的、不同的类型**。于是 `G10nsTimer*` 和 `G10usTimer*` 类型不兼容，一旦传错，部分编译器/MISRA 静态分析工具会报类型不匹配。等于用类型系统帮你挡了一层"单位混用"错误。

### 4. 为将来留独立空间

如果以后某种计时器要加字段（比如 10ms 的想加个暂停累计，像 S10msTimer 那样），独立类型可以各自扩展，互不牵连。你看 S10msTimer/S100msTimer 就已经加了 `PauseFlag`、`TotalTime`，正好印证这个演进路径。

### 一句话总结

这四个结构体**长得一样，但不是一个东西**：G10ns 的时间基准不同，其余靠类型名标注单位。分开 typedef 而不是起别名，一是让编译器/静态工具能区分它们、挡住单位混用，二是让函数名和类型名自解释、三是为各自扩展留余地。这是一种典型的"**用不同类型名表达不同物理单位**"的防御性封装思路，和 MISRA 强调的类型清晰一致。

### 硬件计数器 vs 软件计时器，是两个东西

**硬件计数器（TIMER1 CNT）**：上电后一直自由跑，永不停、永不复位。`GetSysTime()` 只是读它此刻的值。

**软件计时器（G10usTimer 等结构体）**：就是你在内存里定义的一个小变量，里面只有一个 `StartTime` 字段。它不是硬件，不计数，只是**存了一个数字**。

```
硬件计数器：  0 → ... → 123456(当前时刻) → ... → 一直跑
                         │
软件计时器 t: StartTime = ?  ← Res() 做的事就是把当前这个值"抄"下来
```

### "复位"到底干了什么

看 [G10usTimerRes](file:///D:/TopMxx_Oth1/TopMxx_Oth/Driver/Time_Drv.c#L322-L325)：

```c
void G10usTimerRes(G10usTimer *Timer)
{
    Timer->StartTime = GetSysTime();   // 把"当前CNT值"存进 StartTime
}
```

它做的不是"把计数器清零重新开始"，而是：

> **在当前这个时刻，记下时间戳。** 就像你按下秒表的"记忆/起点"按钮——秒表本身没停也没清零，你只是记住了"从这一刻开始算"。

### 为什么"值不固定"也能精确定时

关键是：**计时不靠绝对值，靠"两个不固定值的差值"**。

```
时刻A：调用 Res()
   StartTime = 读CNT = 123456        ← 这个值确实是随机的、不固定的！

       ... 过了 50ms ...

时刻B：调用 Cal() / Over()
   当前CNT = 128456
   经过时间 = 128456 - 123456 = 5000 (个tick)
           = 5000 × 10us = 50ms     ← 起点不固定没关系，差值是固定的！
```

`G10usTimerOver(&t, 5000)` 判断的就是：

```c
(GetSysTime() - Timer->StartTime) > 5000
```

起点 `StartTime` 是 123456 也好、999999 也好，**都会被减法消掉**。你关心的从来不是"现在计数器是几"，而是"**离我记下起点那一刻，过了多久**"。

### 打个比方

想象一把尺子（硬件计数器），刻度从 0 一直画到无穷远，尺子在匀速往前拉，你只能读当前游标位置。

- 你要量一根木头长度，不需要把游标拨回 0
- 只要：木头左端对齐时读一个数 `a`，右端对齐时读一个数 `b`
- 木头长度 = `b - a`
- `a` 是多少无所谓（123 还是 999），只要尺子匀速，`b-a` 就精确

"Res" 就是"读左端并记下来"，"Over/Cal" 就是"读右端做减法"。尺子（CNT）从不复位，也不需要复位。

### 所以三个 Res 函数的区别

你问"这三个函数"（10us/10ms/100ms 的 Res），它们代码几乎一样，都是存当前时间戳：

```c
G10usTimerRes:  StartTime = GetSysTime();   // 存10us刻度
G10msTimerRes:  StartTime = GetSysTime();   // 存10us刻度（换算在Cal/Over里做）
G100msTimerRes: StartTime = GetSysTime();   // 同上
```

差别不在复位，而在**配套的 Cal/Over 怎么解释这个差值**：

```c
G10usTimerCal:  return GetSysTime() - StartTime;           // 直接返回，单位10us
G10msTimerCal:  return (GetSysTime() - StartTime)/1000;    // /1000 → 单位10ms
G100msTimerCal: return (GetSysTime() - StartTime)/10000;   // /10000 → 单位100ms
```

起点都是同一条尺子的读数，只是后面除以不同系数，把 tick 数换算成不同的时间单位给业务层用。

### 一句话总结

> "复位"不是清零硬件计数器，而是**记录当前时间戳作为起点**。计数器跑不跑、起点值固不固定都不重要，因为定时精度来自"**当前值 − 起点值**"这个差值，起点的绝对值被减法消掉了。这正是这套"自由计数器 + 软件时间戳"方案的核心。

### 它的真正用途：I2C 总线挂死时的"时钟拍打"

I2C 有个经典故障：从机（如 EEPROM、传感器）在通信中途掉电或异常，可能把 SDA 线一直拉低不释放。此时主机发任何起始信号都没用，因为 SDA 被从机顶住了。

**恢复方法**就是"**时钟拍打**"（clock toggling）：主机强制把 SCL 线切换成推挽输出，手动产生 9 个时钟脉冲（这里循环 10 次，I2C 协议最多 9 个 clock 就能强制从机释放 SDA），让从机把卡住的状态机走完、释放 SDA。

```c
void I2CClkOut(void)
{
    // 把 SCL(PB8) 从 I2C 复用切成 GPIO 推挽输出
    gpio_mode_set(GPIOB, GPIO_MODE_OUTPUT, ..., mBit8);
    gpio_output_options_set(GPIOB, GPIO_OTYPE_PP, ...);
    for(i=0;i<10;i++)
    {
        GPIO_BOP(GPIOB) = mBit8;   // SCL 高
        Dly1us(3);
        GPIO_BC(GPIOB) = mBit8;    // SCL 低
        Dly1us(3);
    }
    // 打完后，I2CRead/Write 里会再把 PB8 切回复用功能
}
```

这个工程的 I2C 通信主体用的是**硬件 I2C 外设**（I2C0），不是 GPIO 模拟。证据：

- [IIC_Drv.c](file:///D:/TopMxx_Oth1/TopMxx_Oth/Driver/IIC_Drv.c) 里初始化用了 `i2c_init()`、`i2c_master_addressing()` 等硬件 I2C 库函数

### 1. 量级不匹配：NOP 是纳秒级，这里要微秒级

`__NOP()` 是**单条空指令**，200MHz 主频下 1 个 NOP ≈ 5ns。

### 2. 精度：Dly1us 用硬件计数器，NOP 受编译优化影响

`Dly1us` 底层是读 TIMER4（10ns 分辨率）做差值，**延时长度由硬件计数器保证**，和编译器优化等级、CPU 流水线都无关。

`__NOP()` 的实际延时要看：
- 编译器会不会把多个 NOP 优化合并或重排
- CPU 流水线/分支预测导致实际周期数不等于指令数

所以 NOP 延时是"**大概**"，Dly1us 是"**精确**"。I2C 恢复要可靠触发从机状态机，脉冲宽度必须达标，用 Dly1us 更稳。

### 3. 可移植性：主频变了，NOP 延时全乱

如果以后把项目移植到 H743（480MHz），同样 600 个 NOP 变成 1.25us，I2C 时序就不对了。而 `Dly1us(3)` 因为用的是定时器（移植时会重新配置分频），输出仍然是 3us，**代码不用改**。

### 一句话总结

`__NOP()` 适合"凑几个纳秒的极短延时"，`Dly1us` 适合"需要精确微秒级延时"。I2C 时钟恢复需要微秒级且要可靠，所以用 Dly1us。

这个宏是固件库的一个**编码技巧**：把"哪个寄存器 + 寄存器里的哪一位"两个信息打包进一个 32 位整数里。

### 拆解

```c
#define I2C_REGIDX_BIT(regidx, bitpos)  (((uint32_t)(regidx) << 6) | (uint32_t)(bitpos))
```

- `regidx`：寄存器偏移地址（如 STAT0 偏移 = 0x14）
- `bitpos`：该寄存器里的位号（0~31）
- `<< 6`：把寄存器偏移左移 6 位
- `| bitpos`：低位塞入位号

打包后的 32 位值布局：

```
bit 31 ... bit 6 | bit 5 ... bit 0
   寄存器偏移       位号(0~31)
```

为什么左移 6 位？因为位号最大是 31，需要 **5 位**就能表示（0~31），留 6 位足够，还能避免寄存器偏移和位号在低位重叠。

### 举个例子

```c
I2C_FLAG_TBE = I2C_REGIDX_BIT(I2C_STAT0_REG_OFFSET, 7U)
             = (0x14 << 6) | 7
             = 0x500 | 7
             = 0x507
```

一个整数 `0x507` 同时编码了"STAT0 寄存器的第 7 位（TBE=数据寄存器空）"。

### 怎么用：配套的解码宏

光打包没用，还得解出来。看下面两个宏：

```c
#define I2C_REG_VAL(i2cx, offset)   (REG32((i2cx) + (((uint32_t)(offset) & 0x0000FFFFU) >> 6)))  // 右移6位 = 寄存器偏移
#define I2C_BIT_POS(val)            ((uint32_t)(val) & 0x0000001FU)   // 取低5位 = 位号
```

所以 `i2c_flag_get(I2C0, I2C_FLAG_TBE)` 内部大概是这样：

```c
FlagStatus i2c_flag_get(uint32_t i2c_periph, i2c_flag_enum flag)
{
    uint32_t reg_offset = (flag >> 6);          // 解出寄存器偏移
    uint32_t bit_pos    = (flag & 0x1F);        // 解出位号
    uint32_t reg_val    = REG32(i2c_periph + reg_offset);  // 读那个寄存器
    return (reg_val & (1 << bit_pos)) ? SET : RESET;        // 测那一位
}
```

### 为什么要这么绕

这是 GD32/STM32 标准库的通用设计模式（不止 I2C，其他外设也用）。目的是：

**用一个枚举值就能唯一定位"某个寄存器的某一位"**。这样所有标志位（散落在 STAT0、STAT1、SAMCS 等不同寄存器里）可以放在**同一个枚举 `i2c_flag_enum`** 里，用同一个 `i2c_flag_get()` 函数查询。调用者不用关心这个位在哪个寄存器，只传一个枚举值就行。

否则你就得为每个寄存器写一套 `i2c_stat0_flag_get`、`i2c_stat1_flag_get`... 接口会非常啰嗦。

**复位主机的原因**：故障发生时主机的 I2C 外设状态机也可能乱了（比如起始位发出了一半、地址没收到 ACK 等），光 ClkOut 修的是从机，主机自己也得重启。`rcu_periph_reset` 是硬件级复位，比 `i2c_init` 更彻底——把所有寄存器清零，然后 `I2Cx_Drv_Init` 重新配置。

一句话：**先 ClkOut 打醒从机（释放 SDA），再复位+重配主机（清理自身状态），这样总线两端都回到干净起点。**

### 测试逻辑


### 参数含义

| 变量 | 含义 |
|------|------|
| `Addr=0xA2` | FM24CL16 的 I2C 从机地址（7位地址左移1位后的值） |
| `0` | 存储器内部地址，从地址 0 开始读写 |
| `Len=50` | 每次读写 50 字节 |
| `Buff[i]=0x55` | 写缓冲区，固定填 0x55（二进制 01010101，方便看波形） |
| `y[i]=d+1` | 读缓冲区，预填一个非 0x55 的值，读完后如果变成了 0x55 说明读对了 |
| `mTrue` | 16位地址模式标志（FM24CL16 是 16位地址） |
| `d` | 循环计数器，递增，同时用来给读缓冲预填不同值（避免读对了其实是因为没变过） |
| `Wtime` | 一次写+读的耗时，单位 10us |
| `RWOKFlag` | 读写返回值，mTrue=成功，mFalse=失败 |

### 验证思路

每次循环：先把 50 字节 `0x55` 写进去，再把 50 字节读出来到 `y`。读完后检查 `y` 里是不是全变成了 `0x55`——如果是，说明写进去的数据能完整读回来，I2C 读写链路正常。同时 `Wtime` 记录一轮耗时，可以用来评估 I2C 速度。

`y[i] = d+1` 的设计很巧妙：如果读操作实际没执行（比如超时返回了），`y` 里还是预填的 `d+1` 而不是 `0x55`，一看就知道出错了。而 `d` 每轮递增，保证每轮预填值不同，避免"上次读对的残留值碰巧也是 0x55"的假通过。

### 0x55 的用意

`0x55 = 0b01010101`，是经典的测试模式。每一位都在交替，能暴露位级错误（如某根数据线短路、断路）。如果某一位被错误翻转，读回来就不会是 0x55。

一句话：**这是一个 I2C 压力测试，循环写 0x55 再读回来验证，测通信正确性和速度。`y` 预填非 0x55 值防止假通过，`d` 递增保证每轮预填值不同。**
