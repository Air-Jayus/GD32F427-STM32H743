# 注塑机控制工程交互实现流程全面分析

---

## 一、一句话核心结论

**已确认**：当前代码完全支持通过串口连接的显示屏进行软件层面的参数调整，且调整结果能通过 `CC_Read*` 回读指令与 `CC_ReadWorkState` 实时状态查询机制同步反映到显示屏界面；在无注塑机硬件场景下，仍可借助 `CC_Debug_Mode/CC_Debug_Set` 调试指令对 DO/DA 输出进行强制测试并通过工作状态数组观察效果。

---

## 二、生活化小白类比

把整个系统想象成「**一台带按键的智能点菜机（显示屏WM）+ 后厨主机（主板CM）+ 真正的炒菜设备（注塑机硬件）**」：

- **显示屏 WM（Waiter Machine）**：服务员手持点菜机，向厨房写订单（参数设置）、查订单状态（参数回读、工作状态轮询）。
- **主板 CM（Controller Main）**：后厨主机，接收订单写入"内存菜单本"（`ManuPara[]`/`MachPara[]`），异步把菜单誊写到"铁皮账本"（FM24CL64 铁电存储）防掉电。
- **注塑机硬件**：真正执行炒菜的灶台；当前没有灶台，但点菜机和后厨主机仍可互相通信、互相校对菜单，并可通过"调试模式"模拟点亮灶台指示灯（强制 DO/DA）。
- **通信协议**：服务员与后厨之间用对讲机讲固定暗号（`0xF6 0x6F` 起始符 + 功能码 + CRC），主从应答。

## 六、数据流转路径详解

### 6.1 参数调整的「写入-生效-回读」三段闭环

```
┌─────────────────────────────────────────────────────────────────┐
│ ① 写入段：WM 发 CC_LoadMachPara → Ack_LoadFrame() 写 RAM      │
│   CommRecBuff[10+i*4..7+i*4] → MachPara[StartSN+i]            │
│   置 MachParaModifyFlag=mTrue（供应用层感知）                  │
│   置 MachParaSave.{UpdateFlag=mTrue, StartSN, Len}（供RPHA）   │
├─────────────────────────────────────────────────────────────────┤
│ ② 生效段：下一主循环 Action_Pcs() 直接读 MachPara[] 使用       │
│   参数在 RAM 中即时生效，无需等待 EEPROM 写入完成              │
│   写入 EEPROM 是异步的：RPHA_Pcs 每周期仅写 1 个参数           │
│   （[RPHA.c L197-201](file:///D:/TopMxx_Oth1/TopMxx_Oth/Parameter/RPHA.c#L197-L201)）│
├─────────────────────────────────────────────────────────────────┤
│ ③ 回读段：WM 发 CC_ReadMachPara → Ack_ReadFrame() 打包返回     │
│   MachPara[StartSN+i] → CommSendBuff[4+i*4..7+i*4]            │
│   WM 比对写入值与回读值一致 → 界面刷新成功                     │
└─────────────────────────────────────────────────────────────────┘
```

## 八、耦合点、隐藏调用、潜在风险提示

### 8.1 耦合点

1. **`MachPara[]` 双写竞态**：`Ack_LoadFrame`（通信驱动层）与 `RPHA_Pcs`（应用层）都访问 `MachPara[]` 与 `MachParaSave`。代码通过 `usart_interrupt_disable(USART2, USART_INT_RBNE)` 在 [Comm_Drv.c L179](file:///D:/TopMxx_Oth1/TopMxx_Oth/Driver/Comm_Drv.c#L179) 临时关接收中断保证一致性，但 `RPHA_Pcs` 写 EEPROM 期间若来新帧仍可能冲突。
2. **`Code_Pcs` 与 `RPHA_Pcs` 都消费 `GetCommRecCode()`**：`RPHA_Pcs` 优先消费 CC_SnrSetZero/CC_SnrSetLen/CC_CntClr/CC_SetBatchSN（[RPHA.c L237-541](file:///D:/TopMxx_Oth1/TopMxx_Oth/Parameter/RPHA.c#L237-L541)），`Code_Pcs` 在其后处理剩余指令。**顺序固定**：Main.c 中 RPHA_Pcs 在 Code_Pcs 之前。
3. **互连代码校验**：[RPHA.c L187-191](file:///D:/TopMxx_Oth1/TopMxx_Oth/Parameter/RPHA.c#L187-L191) 检查 `HardConf_HardConfLinkCode/Para_MachParaLinkCode/Para_ManuParaLinkCode` 与软件编译宏 `mCMSoftHardConfLinkCode/mCMSoftMachParaLinkCode/mCMSoftManuParaLinkCode` 是否匹配，不匹配会报警 `mAlarm_SoftParaLinkCodeErr`。**风险**：若 WM 程序版本与 CM 不一致，会触发此报警。

### 8.2 隐藏调用

1. **`Ack_LoadFrame` 中对 `PeriParaWriteReq` 的填充**（[Comm_Drv.c L472-473](file:///D:/TopMxx_Oth1/TopMxx_Oth/Driver/Comm_Drv.c#L472-L473)）：外设参数加载时，会额外把首参数填入 `PeriParaWriteReq` 结构，推测用于触发外设（如 J6h 卡）同步下发，但**只填了首参数**，多参数时其余参数不会触发该机制。
2. **电子尺长度校准的零点同比例修改**（[RPHA.c L309-379](file:///D:/TopMxx_Oth1/TopMxx_Oth/Parameter/RPHA.c#L309-L379)）：用户修改尺长度时，**零点会按比例自动调整**，避免位置突变。这是隐式行为，用户可能不知零点也被改了。
3. **累加和重算与二次配置**（[RPHA.c L204-206](file:///D:/TopMxx_Oth1/TopMxx_Oth/Parameter/RPHA.c#L204-L206)）：所有机器参数写完后，会重算 `MachPara[0]`（累加和）并调用 `MachParaReConf()`。当前 `MachParaReConf()` 为空函数（[RPHA.c L589-591](file:///D:/TopMxx_Oth1/TopMxx_Oth/Parameter/RPHA.c#L589-L591)），是预留扩展点。

### 8.3 潜在风险

1. **EEPROM 写入失败未阻断流程**：[RPHA.c L208-212](file:///D:/TopMxx_Oth1/TopMxx_Oth/Parameter/RPHA.c#L208-L212) 仅在所有参数写完后才报警 `mAlarm_MachParaSaveErr`，期间用户可能误以为参数已保存成功。
2. **回读超时未显式处理**：`Ack_LoadFrame/Ack_ReadFrame` 调用 `EnCommTxInt()` 启动发送，但若发送中断未触发（硬件故障），无超时重发机制。
3. **WM 回读延时**：[Comm_Drv.c L425-426 注释](file:///D:/TopMxx_Oth1/TopMxx_Oth/Driver/Comm_Drv.c#L425-L426) 提到"界面程序：回读后才会发下一加载帧，长帧回读延时时间500ms"——即参数加载是非流水线式的，每帧加载后必须等 500ms 才能下一帧，**大批量参数修改耗时较长**。

```
┌────────────────────────────────────────────────────────────────┐
│ HMI 层（显示屏 WM，外部设备）                                   │
│  - 按键采集 → 组帧 CC_Load*/CC_Read*/CC_Debug_Set/mCode_*      │
│  - 接收响应帧 → 解析 → 界面刷新                                 │
│  - 周期性轮询 CC_ReadWorkState → 主界面实时数据                │
└──────────────────────┬─────────────────────────────────────────┘
                       │ USART2 PD8/TXD0, PD9/RXD0, 115200bps 9位奇校验
                       │ 帧: 0xF6 0x6F + SN/LEN + FuncCode + Params + CRC
┌──────────────────────▼─────────────────────────────────────────┐
│ 驱动层（Comm_Drv.c）                                            │
│  - USART2_IRQHandler → CommRecIRQPcs() 状态机收帧             │
│  - Comm_Drv_Pcs() 解析帧、调用 Ack_LoadFrame/Ack_ReadFrame     │
│  - 维护 ParaModifyFlag/ManuParaModifyFlag/MachParaModifyFlag  │

│  - 提供 GetCommRecCode/GetCommRecCodePara0~4 API 供上层        │
└──────────────────────┬─────────────────────────────────────────┘
                       │ 共享 RAM 数组: ManuPara/MachPara/PeriPara/HardConf/WorkState
┌──────────────────────▼─────────────────────────────────────────┐
│ 业务/应用层（Application + Parameter）                         │
│  - RPHA_Pcs: 异步持久化到 FM24CL64（I2C）                      │
│  - Code_Pcs: 处理 CC_Debug_Set/CC_SnrSetZero/CC_CntClr 等     │
│  - Action_Pcs + Scheduler_Pcs: 读 MachPara/ManuPara 执行动作   │

└────────────────────────────────────────────────────────────────┘
```

**关键关联点**：
- 驱动层与应用层**通过全局数组解耦**：`ManuPara[]`/`MachPara[]`/`WorkState[]` 是共享内存，无函数调用耦合。
- 修改标志机制（`ParaIsModify` 等）让应用层**被动感知**参数变更，避免每周期全量重算。
- `WorkState[]` 是**单向数据流**：应用层各模块只写，驱动层 `Ack_ReadFrame` 只读，无锁冲突。

# 全局数组解耦机制详解

## 一、一句话核心结论

**已确认**：`ManuPara[]`、`MachPara[]`、`WorkState[]` 等全局数组确实是驱动层与应用层之间的**数据交换中间媒介**——遵循"**写入方与读取方互不相识，只共同遵守数组数据格式约定**"的共享内存（Blackboard 公布板）模式，实现层间解耦；驱动层 Comm_Drv 写参数到 `MachPara[]`、读 `WorkState[]` 返回给显示屏，应用层各 `_Pcs` 函数读 `MachPara[]` 执行动作、把状态写进 `WorkState[]`，双方无需直接函数调用。

---

## 二、生活化小白类比

把全局数组想象成**「超市里的开放式货架」**：

- **货架（全局数组）**：摆在超市中央，所有部门都能看到、都能访问。
- **采购部（驱动层 Comm_Drv）**：把供货商送来的货物（WM 写入的参数）**摆上货架**，也可以**从货架取货**打包给顾客（WM 回读）。
- **销售部（应用层 Action/Scheduler）**：**从货架取货**（读 MachPara）用来执行动作（炒菜），把销售情况（位置/压力/温度）**摆回货架**（写 WorkState）。
- **仓管部（RPHA_Pcs）**：定期把货架上的货物**抄写到铁皮账本**（FM24CL64 EEPROM），掉电不丢。

关键点：**采购部、销售部、仓管部互不见面**，他们只跟货架打交道。采购部不知道销售部何时取货，销售部也不知道采购部何时补货。**唯一的契约是「货物必须放在指定货架位置的指定格子里」**（即数组下标 `mPara_xxx` 和 `mState_xxx` 宏定义）。

如果改成"直接调用"模式（强耦合），相当于采购部每次进货都得打电话通知销售部"我来货了，你赶紧取"——采购部必须知道销售部的电话号码（函数地址），销售部换人就完蛋。**解耦的本质是用"数据空间"代替"控制流"做通信**。

---

## 三、该内容在注塑机系统中的位置与作用

这个"共享内存解耦"机制位于**系统纵向分层架构的纵向通信主干**上，是连接 HMI/驱动/业务三层的**数据总线**：

```
┌──────────────────────────────────────────────────┐
│ HMI 层（显示屏 WM，外部）                         │
│   按键 → 组帧 → 串口                              │
└──────────────────────┬───────────────────────────┘
                       │ USART2 串口字节流
┌──────────────────────▼───────────────────────────┐
│ 驱动层（Comm_Drv.c 等）                           │
│   Ack_LoadFrame() ──写──→ ┌──────────────┐       │
│   Ack_ReadFrame() ──读──→ │ 全局数组层    │       │
│   各 _Drv_Pcs()    ──写──→ │ (中间媒介)    │       │
│                            │ ManuPara[]    │       │
┌──────────────────────────┐│ MachPara[]    │       │
│ 应用层（Action/Scheduler ││ PeriPara[]    │       │
│   /Temp/Position/HAI...）││ HardConf[]    │       │
│   Action_Pcs() ──读──→   ││ WorkState[]   │       │
│   各 _Pcs()    ──写──→   │└──────────────┘       │
│   RPHA_Pcs()   ──读/写──→│   ↑               │   │
└──────────────────────────┘   │ 定义于RPHA.c   │   │
                               │ extern于其他   │   │
                               └──────────────┘   │
└──────────────────────────────────────────────────┘
```

**作用**：
1. **消除函数调用依赖**：驱动层不需要 `#include "Action.h"`，应用层也不需要 `#include "Comm_Drv.h"`，双方只引用 `Parameter/` 下的 .h 文件。
2. **统一数据契约**：所有层通过 `mPara_xxx`（参数序号宏）和 `mState_xxx`（状态序号宏）访问数组，**序号宏就是契约**。
3. **支持异步处理**：驱动层收帧写入后立刻返回，应用层在下一主循环才处理；应用层写状态后立刻返回，驱动层下次被 WM 查询时才读——天然解耦时序。

**核心解耦特征**：
1. 驱动层 Ack_LoadFrame 与应用层 Action_Pcs **从不互相调用**，都只跟 `MachPara[]` 打交道。
2. 应用层 Temp_Pcs 写 `WorkState[mState_Zone1Temp]` 后立刻返回，不通知驱动层；驱动层下次被 WM 查询时自己去读——**生产者不关心消费者何时消费**。
3. 写入与读取**无锁**，但通过"主循环串行执行"保证时序安全（见下文风险点）。

## 七、耦合点、隐藏调用、潜在风险

### 7.1 耦合点（看似解耦实则仍有约束）

1. **数据格式契约耦合**：驱动层与应用层必须**对数组下标的语义有一致理解**。如果应用层把 `mPara_SysPresMax` 从 10 改成 11，而 WM 程序还按 10 发帧，就会写错位置。这种耦合是**隐式的**，编译器检测不到。
2. **修改标志位耦合**：驱动层 [Comm_Drv.c L408](file:///D:/TopMxx_Oth1/TopMxx_Oth/Driver/Comm_Drv.c#L408) 写 `ManuParaModifyFlag=mTrue`，应用层通过 `ManuParaIsModify()` 查询。这相当于驱动层向应用层发了一个"事件通知"，但通过全局变量传递而非函数调用——**仍然是耦合，只是弱化了**。
3. **顺序依赖**：`RPHA_Pcs` 在主循环中必须**早于** `Action_Pcs`（[Main.c L176-188](file:///D:/TopMxx_Oth1/TopMxx_Oth/Main.c#L176-L188)），因为 RPHA 要先把 EEPROM 中的参数加载到数组、处理校零/计数清零，Action 才能用最新值。这种顺序约束是**隐式的**，注释里没写。

### 7.2 隐藏调用（容易被忽略的访问点）

1. **`State_xxx` 宏别名**：`State_ShotCntLW`、`State_Zone1Temp` 等并非独立变量，而是 `WorkState[mState_xxx]` 的宏别名。表面看是"赋值变量"，实际是"写数组"——**容易让人误以为是局部状态**。
2. **`Para_xxx` 宏别名**：`Para_SysPresMax` 等同理，写 `Para_SysPresMax = 200` 实际是 `MachPara[10] = 200`。如果开发者在动作函数里写 `Para_SysPresMax++` 这种自增，**会触发 EEPROM 保存标志（如果有的话）**，可能产生意外副作用。
3. **中断与主循环共享数组**：`CommRecBuff[]`/`CommSendBuff[]` 被 USART2 中断和 `Comm_Drv_Pcs` 主循环共同访问。代码用 `usart_interrupt_disable(USART2, USART_INT_RBNE)` 在 [Comm_Drv.c L179](file:///D:/TopMxx_Oth1/TopMxx_Oth/Driver/Comm_Drv.c#L179) 临时关中断保护——**这是隐藏的临界区保护**，如果开发者复制这段代码时漏了关中断，就会出竞态。

### 7.3 潜在风险

1. **无锁并发写**：`MachPara[]` 可被 `Ack_LoadFrame`（驱动层）和 `RPHA_Pcs`（应用层）同时访问。虽然主循环串行执行保证大多数情况安全，但 **`Ack_LoadFrame` 是在 `usart_interrupt_disable` 内执行的**，而 `RPHA_Pcs` 在主循环中执行——如果 `RPHA_Pcs` 正在写 `MachPara[0]`（累加和），此时来一个 CC_LoadMachPara 帧触发 `Ack_LoadFrame` 写 `MachPara[10]`，**逻辑上不冲突**（不同下标），但**语义上冲突**（累加和还没算完就被改了值）。
2. **WorkState 单向流动假设**：代码假设 `WorkState[]` 只被应用层写、驱动层读。但如果未来有人在驱动层误写 `WorkState[]`（比如某个驱动 _Pcs 想反馈状态），就会**破坏单向数据流契约**，导致 WM 读到不一致数据。
3. **数组越界**：`Ack_LoadFrame` 有溢出检查（[L399-400](file:///D:/TopMxx_Oth1/TopMxx_Oth/Driver/Comm_Drv.c#L399-L400)），但 `Ack_ReadFrame` 的检查在 [L528-529](file:///D:/TopMxx_Oth1/TopMxx_Oth/Driver/Comm_Drv.c#L528-L529)——如果 WM 发来错误的 SN/Len，虽会 return 但**不报警**，调试时难以发现。

## 总结回答用户的核心疑问

**"这些全局数组是否作为数据交换的中间媒介？"** —— **是**，这是教科书式的"共享内存解耦"（Blackboard Pattern）实现。

**"当驱动层或显示模块产生数据改变时，这些变化是否会被存储到全局数组中，然后再由驱动层或显示模块进行调用和处理？"** —— **部分正确，但需要澄清两点**：

1. **驱动层确实直接读写数组**：`Ack_LoadFrame` 收到 WM 帧后直接写 `MachPara[]`，`Ack_ReadFrame` 被 WM 查询时直接读 `WorkState[]`——驱动层是数组的直接访问者。

2. **"显示模块"本身不直接访问数组**：显示屏 WM 是外部设备，**它不直接读写 CM 的全局数组**，而是通过串口协议与 CM 的驱动层通信，由驱动层代为读写数组。**WM 看不到 `MachPara[]` 的存在**，它只知道"发 CC_ReadMachPara 帧能拿到 4 字节参数值"。

3. **"变化存储→调用处理"的描述要修正**：不是"存储后被动调用处理"，而是"存储后由对方在下次主循环主动查询处理"。**生产者不通知消费者，消费者自行轮询**——这是共享内存模式的本质特征，与"事件驱动"（生产者通知消费者）形成对比。`ParaIsModify()` 标志位是一种**弱事件通知**，让消费者不必每周期全量重算，但仍需消费者主动调用该函数查询。

**这种解耦的本质**：用**数据空间**（数组下标）代替**控制流**（函数调用）做层间通信。代价是调试可读性下降、隐式契约增加；收益是层间无函数依赖、支持异步处理、零拷贝实时性好。这是嵌入式实时控制系统的典型架构选择。

## 二、生活化小白类比

把整个系统想象成**「一家餐厅」**：

- **WM（显示屏）** = 顾客手里的**点菜平板**。它是一个独立的硬件设备，有自己的屏幕和触摸/按键，有自己的操作系统（可能是 Linux）和 App 程序。

## 五、WM 到底属于什么层？

### 5.1 从"经典分层架构"视角

如果用经典的软件分层术语来套整个系统（CM + WM 合在一起看）：

| 经典分层 | 在本系统中的对应 | 是否在当前工程 |
|---|---|---|
| **表示层（Presentation）** | **WM 显示屏**（界面渲染、按键输入、数据展示） | ❌ 不在 |
| **业务层（Business）** | CM 应用层（Scheduler、Action、Alarm、Temp） | ✅ 在 |
| **数据层（Data）** | CM 参数层 + EEPROM（ManuPara、MachPara、FM24CL64） | ✅ 在 |
| **驱动层（Driver/ HAL）** | CM 驱动层（Comm_Drv、DIDO_Drv、DAC_Drv） | ✅ 在 |

所以 **WM 属于「表示层 / HMI 层」**，**业务层是 CM 的应用层**。两者是**对等的相邻层**，不是包含关系。

### 5.2 从"嵌入式控制系统"视角

注塑机行业通常把系统分成：

| 术语 | 对应 | 说明 |
|---|---|---|
| **HMI 层**（人机界面） | WM 显示屏 | 人机交互，显示参数/状态、接收按键 |
| **CM 层**（控制主机） | 当前工程全部（驱动+应用+参数+动作） | 工艺控制、运动控制、IO 控制 |
| **执行层** | 注塑机硬件（油泵/油缸/电机） | 执行 CM 的控制指令 |

在这个划分下，**WM = HMI 层**，CM 内部再分驱动/应用/参数层。WM 和 CM 的应用层是**同一层级的不同部分**，通过串口协议通信。

## 六、为什么 WM 不能算"业务层"

业务层的定义是：**封装业务规则和业务逻辑，直接操作领域数据并反映业务状态变化的软件层**。

对照这个定义看 WM：

| 判断维度 | 业务层特征 | WM 的实际行为 |
|---|---|---|
| 是否执行业务规则 | 如"保压时间到才能切换" | ❌ WM 不执行工艺规则，只是把用户输入发给 CM |
| 是否控制硬件 | 直接/间接控制执行机构 | ❌ WM 不控制任何注塑机硬件 |
| 是否保存业务数据 | 保存工艺参数、配方 | ❌ WM 不保存参数，参数存在 CM 的 EEPROM |
| 是否反映业务状态 | 计算/推导业务状态 | ❌ WM 只显示 CM 发来的 WorkState，不自己计算 |

WM 做的事情是：
- **接收用户输入**（按键/触摸）
- **把输入编码成协议帧**发给 CM
- **接收 CM 返回的数据**
- **渲染到屏幕**

这完全是**表示层（输入输出）的职责**，不是业务层。真正的业务逻辑（如"注射压力不能超过系统压力最大值"、"关模低压超时要报警"）都在 CM 的应用层 [Action/](file:///D:/TopMxx_Oth1/TopMxx_Oth/Action) 和 [Application/](file:///D:/TopMxx_Oth1/TopMxx_Oth/Application) 中执行。

## 八、为什么容易产生混淆

容易混淆的原因是 WM 和 CM 应用层之间有个"假象"：

1. **协议帧里带业务语义**：`CC_LoadMachPara` 看起来像"业务指令"，但这只是**通信协议的命名**，不代表执行业务。就像 HTTP 请求里 `POST /api/order` 带业务语义，但 HTTP 协议本身不是业务层。
2. **WM 会做一些简单校验**：比如输入范围检查、参数单位转换。但这是**表示层的数据格式化**，不是业务规则——真正的业务规则校验（如"系统压力不能超过 140bar"）在 CM 应用层。
3. **界面上能看到工艺参数**：用户在 WM 上看到的"保压压力 80bar"，这个值**存储在 CM 的 MachPara[] 里**，WM 只是把它从 CM 读过来显示。WM 关机再开，这个值还在（因为存在 CM 的 EEPROM）。

**判断某段逻辑属于哪层的简单方法**：问自己"如果 WM 断电了，这个逻辑还在不在？"——如果还在（因为跑在 CM 上），就是 CM 的层；如果不在了，就是 WM 的层。
